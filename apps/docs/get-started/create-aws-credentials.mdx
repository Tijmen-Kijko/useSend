---
title: Create AWS credentials
description: Create least-privilege AWS credentials for a self-hosted useSend instance.
---

useSend needs AWS SES for sending and domain management, SNS for delivery-event
callbacks, and STS to resolve the AWS account ID. Give the useSend workload its
own IAM identity; do not reuse the root account or a general administrator
credential.

<Steps>
  <Step title="Create a dedicated IAM identity">
    In AWS IAM, create a dedicated identity for the useSend production
    workload. On a non-AWS server this can be an IAM user with programmatic
    credentials. If useSend itself runs on AWS, prefer a workload role and the
    AWS SDK default credential provider chain.

    Do not attach `AdministratorAccess`, `AmazonSESFullAccess`, or
    `AmazonSNSFullAccess`.

    ![create user](/images/aws/key-1.png)
  </Step>

  <Step title="Attach an action-scoped policy">
    Create a customer-managed policy containing only the AWS actions the
    current useSend mail path invokes. Replace `<aws-region>` with the SES
    region you selected.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UseSendSesAndSns",
      "Effect": "Allow",
      "Action": [
        "ses:CreateEmailIdentity",
        "ses:DeleteEmailIdentity",
        "ses:GetEmailIdentity",
        "ses:PutEmailIdentityMailFromAttributes",
        "ses:SendEmail",
        "ses:GetAccount",
        "ses:CreateConfigurationSet",
        "ses:CreateConfigurationSetEventDestination",
        "ses:DeleteSuppressedDestination",
        "ses:CreateTenantResourceAssociation",
        "ses:DeleteTenantResourceAssociation",
        "sns:CreateTopic",
        "sns:DeleteTopic",
        "sns:Subscribe",
        "sns:ConfirmSubscription"
      ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:RequestedRegion": "<aws-region>"
        }
      }
    },
    {
      "Sid": "UseSendCallerIdentity",
      "Effect": "Allow",
      "Action": "sts:GetCallerIdentity",
      "Resource": "*"
    }
  ]
}
```

    This policy is action-scoped rather than full-access. Once your sending
    domains, SNS topic names and configuration-set naming are stable, you can
    further restrict resources where the relevant AWS APIs support resource
    scoping.

    ![set permission](/images/aws/key-2.png)
  </Step>

  <Step title="Create credentials only when required">
    On a VPS or other non-AWS host, create an access key for the dedicated IAM
    identity.

    ![create access key](/images/aws/key-3.png)
    ![option and create](/images/aws/key-4.png)
    ![description](/images/aws/key-5.png)

    Inject the values through your deployment secret store. Do not commit a
    populated `.env` file to Git.

```env
AWS_ACCESS_KEY_ID=<access-key-id>
AWS_SECRET_ACCESS_KEY=<secret-access-key>
```

    Both variables must be set together. If both are omitted, useSend falls
    back to the AWS SDK default credential provider chain.

    ![create access key](/images/aws/key-6.png)
  </Step>

  <Step title="Verify and rotate">
    After configuring the credential, verify that useSend can read the SES
    account, configure the chosen region, and perform one controlled test send.

    For rotation:

    1. Create a second credential for the same least-privilege identity, or a
       new identity with the same policy.
    2. Put the replacement values in the deployment secret store and
       restart/redeploy useSend.
    3. Verify SES settings and perform a controlled test send.
    4. Disable the old credential.
    5. After the observation window, delete the old credential.

    If a credential is suspected to be exposed, skip the observation delay:
    replace it, verify the replacement, and disable the old credential
    immediately.
  </Step>
</Steps>

<Warning>
AWS platform credentials and useSend project API keys are separate security
boundaries. A leaked application API key should be revoked by replacing only
that project's useSend key; it should not require rotating the AWS identity.
</Warning>
